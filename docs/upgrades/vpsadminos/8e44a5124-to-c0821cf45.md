# vpsAdminOS 8e44a5124 to c0821cf45

This guide covers vpsAdmin's vpsAdminOS input transition from
`8e44a5124439b1f3048ffc56b1717614a5360358` to
`c0821cf45a8aad980c11ace74d6ae6bf6b79067e`. It includes the upstream changes
adopted between those revisions and the first-running projection retained for
the current boot by [boot monitoring](../../boot-autostart.md). Read the
[vpsAdminOS compatibility contract](../../vpsadminos-compatibility.md) before
selecting a node generation or rollback target.

## Adopted recovery semantics

Upstream commit
[`22d31594cab9d4984ff19414e7af555e3f30f945`](https://github.com/vpsfreecz/vpsadminos/commit/22d31594cab9d4984ff19414e7af555e3f30f945)
introduces persisted container `recovery_tainted`, saved error state and veth
`host_link` ownership metadata. The selected osctld can load older pool
configuration and save that metadata during normal management, without a new
numbered osup migration.

The previous `8e44a5124439b1f3048ffc56b1717614a5360358` daemon ignores the guard
and drops the metadata when saving. After the selected daemon manages a pool,
downgrading it to that previous input or another daemon lacking those recovery
semantics is unsupported. Retain a recovery-aware generation and fix forward,
as described in the compatibility contract. This transition provides no
downgrade conversion.

The selected
[osctl recovery-command reference](https://github.com/vpsfreecz/vpsadminos/blob/c0821cf45a8aad980c11ace74d6ae6bf6b79067e/osctl/man/man8/osctl.8.md)
describes cleanup and host-link ownership checks for the supported daemon.
Those operations do not establish downgrade support.

## Deployment order

The lock update selects build inputs; it does not deploy nodes or rebuild guests.
Keep kernel and OpenZFS generations paired. The selected vpsAdminOS
[update guide](https://github.com/vpsfreecz/vpsadminos/blob/c0821cf45a8aad980c11ace74d6ae6bf6b79067e/docs/os/updates.md)
also describes kernel activation, resolver ownership and userspace mount
restrictions. Existing guests adopt guest configuration changes independently.

Deploy additive supervisor RPC support, then the provider and consumer node
packages. Each node captures its cohort on its next actual boot. Upgrade node
producers before deploying monitoring rules that use only boot-obligation metrics.
Older nodes without the new metric family have no per-VPS boot-autostart coverage
from those rules.
No coordinated fleet reboot is required. Follow
[boot monitoring upgrade and recovery](../../boot-autostart.md#upgrade-and-recovery)
for unavailable evidence and normal boot activation.
